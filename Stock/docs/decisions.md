# Décisions de réalisation — Stock (et réorganisation du dépôt)

Choix faits pendant la réalisation lorsque la spécification laissait une marge d'interprétation (même format que `Annuaire/docs/decisions.md`).

| # | Sujet | Décision | Raison |
|---|---|---|---|
| 1 | Migrations communes pendant R1 | Au jalon R1, les projets de migrations existants (`Barthazon.Migrations.Sqlite` / `.Postgres`, schéma commun) sont placés provisoirement dans `Portail/src/` ; ils sont remplacés au jalon R2 par des migrations par application. Les tests du référentiel chargent provisoirement le module de l'annuaire (le modèle doit correspondre aux migrations communes). | R1 ne change pas le schéma ; R2 découpe les contextes. |
| 2 | Hôte de test générique | `Socle/tests/Support` expose `TestApplication.CreateAsync(configure, settings, modules)` et `TestApplicationBuilder.AddModule(persistance, services)` ; chaque application a son raccourci (`CatalogTestApp`). | Le support de test ne référence plus l'annuaire (6.2). |
| 3 | Version par application | Chaque dossier a un `Directory.Build.props` qui importe celui de la racine et fixe `<Version>` ; l'état du système affiche la version du socle, du portail et de chaque application (version de l'assemblage d'interface du module). | Section 6.1. |
| 4 | Contexte du socle | `SocleDbContext` vit dans `Shared.Infrastructure` ; les mappings du référentiel y sont ajoutés par `AddSocleMappings(assembly)` (le socle technique ne référence pas le référentiel). | `Shared.Infrastructure` est référencé par `Referential.Infrastructure`, pas l'inverse. |
| 5 | Déclaration d'une base | `IModulePersistence` ne porte plus d'assemblage de mappings : chaque application déclare sa base par `AddModuleDatabase<TContext>(Info, fabrique)`, où `Info` (`ModuleDatabaseInfo`) donne clé, ordre, table d'historique, assemblages de migrations et préfixes de tables. | Un seul point de déclaration, utilisé par l'initialisation, l'export JSON, `/health` et l'administration. |
| 6 | Reprise d'une base existante | Une application dont les tables existaient déjà (`AdoptsLegacySchema`) voit sa **première migration** inscrite comme appliquée lors de la reprise. La reprise n'a lieu que si l'ancienne table contient une des migrations `Initial` connues et si aucune nouvelle table d'historique n'est remplie. | Section 6.6 ; aucune donnée n'est touchée. |
| 7 | Tables d'une application | Les tables appartenant à un contexte sont reconnues par leurs préfixes déclarés (le journal commun est mappé partout mais n'appartient qu'au socle). | L'information « exclue des migrations » n'est pas disponible dans le modèle d'exécution d'EF Core. |
| 8 | Fixture de reprise | `Portail/tests/Barthazon.Integration.Tests/Fixtures/barthazon-v1.db` et `barthazon-v1.json` ont été générés avec la version 1 (données de démonstration, trois comptes, un favori) avant toute modification du jalon R2. Mot de passe de l'administrateur de la fixture : `Barthazon2026`. | Section 6.6. |
